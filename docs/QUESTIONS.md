## Operations

1. **Vercel domain-record issue for `nifty-leads.vercel.app` (17 Oct 2026):** With the hostname present as a *domain record* (Settings → Domains), Vercel's edge returns `404 NOT_FOUND` globally (verified from multiple PoPs) despite a correct `verified: true` record and alias binding. As a *pure alias* (no domain record) the same hostname routes correctly. Resolution: the domain record is permanently removed from the dashboard, and `pnpm run deploy` (`scripts/deploy.sh`) re-binds the alias after every production deploy, because pure aliases do not auto-rebind. Safe default: never re-add `nifty-leads.vercel.app` in the Domains UI. Open question for Vercel support: why the domain-record binding fails for this hostname.
2. Supabase `DATABASE_URL` uses port `5432` (direct). If connection pooling is needed later, switch to the pooler URI (port `6543`) — pooler requires `?sslmode=require` and prepared-statement config for pg/drizzle.
3. **Migration renumber (17 Oct 2026):** drizzle-kit was upgraded 0.30.6 → 0.31.11 (0.30.6 cannot load TS configs under Node 24). The regenerated journal produced `0000_faithful_thor_girl.sql` (full create of the current schema, including the better-auth `verifications.updatedAt`/nullable `type` fixes); the superseded `0001_initial.sql` was removed. Phase 0/1A docs still mention `0001_initial.sql` — historical records, not current state. A local Docker database migrated under the old file needs a volume reset (`docker compose down -v`) before re-running `pnpm run db:migrate`. Supabase was never migrated, so it just runs `0000`.
4. **Admin first login:** `BETTER_AUTH_URL=https://nifty-leads.vercel.app` is set as a Vercel env var. With no email provider configured, the OTP code is logged to the function logs — read it once from Vercel Dashboard → Deployments → Logs, then configure a provider (Section 8.5) from Admin Settings. Users in `ADMIN_EMAILS` get the `admin` role at sign-up (wired in `databaseHooks.user.create.before`).
5. **Supabase connection from Vercel (18 Oct 2026):** free-plan direct host `db.<ref>.supabase.co` resolves **AAAA only** (IPv6); Vercel functions are IPv4-only, so it fails with `getaddrinfo ENOTFOUND`. The app must use the **Session pooler** string from the dashboard Connect dialog (`postgresql://postgres.<ref>:…@aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=require`). The pooler host/region cannot be guessed — it must be copied from the dialog. The direct host still works from IPv6-capable local networks. Env values are write-only (`sensitive`): they cannot be read back via dashboard, API, or `vercel env pull` — verify a suspected bad value by the hostname in the runtime error logs. Also: the short alias stays pinned to the last `pnpm run deploy` target; a dashboard Redeploy does **not** move it (only the long `nifty-leads-madansa7s-projects.vercel.app` domain updates), so after any dashboard redeploy run `pnpm run deploy` to rebind.
6. **better-auth 1.7.10 schema requirements (18 Oct 2026):** both failures surface only at the first real DB write (not at boot), and both are now fixed: (a) `advanced.database.generateId: "serial"` in `apps/web/src/lib/auth.ts` is required — better-auth defaults to random *string* ids, which Postgres rejects (`22P02 invalid input syntax for type integer`) against our integer serial PKs; (b) `users.email_verified` must be **boolean** (better-auth writes `true` on every OTP sign-in) — the original `timestamp` column threw `a.toISOString is not a function` *after* OTP verification succeeded, which the login UI then surfaced as "Wrong code or expired". Migration `0001_aspiring_carlie_cooper.sql` adds `USING false` because drizzle-kit emits a bare `SET DATA TYPE boolean` and Postgres has no implicit timestamp→boolean cast; applied to Supabase as `user_email_verified_boolean` (table was empty).
7. **OTP semantics for support (18 Oct 2026):** one record per identifier — resending **replaces** the previous code, 3 typing attempts max, 5-minute expiry, and a successful verification **deletes** the record. When relaying a code from the logs, always use the newest `[auth] sign-in OTP` line and warn the user not to click "Send code" again afterwards.
